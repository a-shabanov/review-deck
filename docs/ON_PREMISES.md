# Review Deck на своей инфраструктуре

Один сервер Review Deck обслуживает одну медиатеку и общую разметку через браузер. Исходные видео остаются на вашем диске/NAS. Все операции выполняются локальными Python и ffmpeg; облачные API, телеметрия и CDN не используются. Серверу не нужен интернет во время работы. Интернет требуется при сборке образа для получения Python, ffmpeg и Waitress; готовый образ можно перенести в закрытую сеть.

## Быстрый запуск (Linux, Docker Compose v2)

1. Скопируйте весь проект на сервер и перейдите в его каталог. Подготовьте отдельные каталоги медиатеки и данных. Пример ниже использует `/srv/media` и `/srv/review-deck-data`. Не кладите каталог данных внутрь медиатеки или наоборот.

   ```sh
   sudo mkdir -p /srv/media /srv/review-deck-data
   sudo chown 10001:10001 /srv/review-deck-data
   cp .env.example .env
   ```

2. В `.env` задайте абсолютные пути `REVIEW_DECK_LIBRARY=/srv/media` и `REVIEW_DECK_DATA_DIR=/srv/review-deck-data`. UID/GID по умолчанию — `10001:10001`. Этот пользователь должен читать видео, проходить по подкаталогам медиатеки и записывать данные. Для NAS с другими правами задайте соответствующие UID/GID в `.env`. На Docker Desktop права bind mounts обрабатывает Docker Desktop; дайте Docker доступ к обоим каталогам.

3. Создайте пароль (не меньше 16 символов) в отдельном файле. Он вводится скрыто; в `.env` пароль не записывается. Каталог `secrets` доступен только владельцу, файл внутри него читается непривилегированным пользователем контейнера через Docker secret mount.

   ```sh
   mkdir -m 700 secrets
   python3 - <<'PY'
   import getpass, os
   from pathlib import Path
   first = getpass.getpass('Пароль Review Deck (16+ символов): ')
   second = getpass.getpass('Повторите пароль: ')
   if first != second or len(first) < 16 or '\n' in first or '\r' in first:
       raise SystemExit('Пароли не совпадают или пароль слишком короткий')
   p = Path('secrets/review-password.txt')
   with p.open('x') as f:
       f.write(first + '\n')
   os.chmod(p, 0o444)
   PY
   ```

4. До первого запуска перенесите прежнюю разметку, если она есть (см. ниже). Затем:

   ```sh
   docker compose config --quiet
   docker compose up -d --build
   docker compose ps
   docker compose logs --tail=50 review-deck
   ```

5. С хоста сервера откройте `http://127.0.0.1:8765`. Браузер запросит логин `review` (или `REVIEW_DECK_USER` из `.env`) и заданный пароль. Для доступа с другого компьютера настройте HTTPS ниже. Приложение ожидает размещение в корне отдельного домена, без URL-префикса.

`GET /healthz` возвращает `{"status":"ok"}` без пароля, без путей и названий видео. Docker проверяет его каждые 30 секунд. Остальные страницы, API, видео и изображения требуют авторизации. Состояние `unhealthy` само по себе не перезапускает контейнер: `restart: unless-stopped` перезапускает завершившийся процесс; на `unhealthy` настройте оповещение в своём мониторинге.

## HTTPS и сеть

По умолчанию порт опубликован только на `127.0.0.1`. Для браузеров в LAN поставьте перед ним существующий HTTPS-прокси вашей организации. В `deploy/Caddyfile.example` есть минимальный пример Caddy, работающего на том же хосте: внутренний домен `review.example.internal` → `127.0.0.1:8765`, сертификат внутреннего CA. Установите доверие к CA на клиентских компьютерах либо используйте свой корпоративный сертификат. Имя домена должно разрешаться во внутреннем DNS.

В `.env` укажите точный адрес браузера без пути и завершающего слеша:

```dotenv
REVIEW_DECK_PUBLIC_ORIGIN=https://review.example.internal
```

После изменения `.env`: `docker compose up -d`. Прокси должен сохранять `Host`, `Authorization`, `Origin` и `Range`, допускать JSON-тела до 16 MiB и достаточно долго ждать генерации превью. Пример Caddy использует стандартную передачу этих заголовков. Не удаляйте `Authorization` на прокси. Пароль HTTP Basic передаётся с каждым запросом, поэтому доступ по сети должен идти через HTTPS или защищённый SSH-туннель. Проверить удалённо без прокси можно туннелем `ssh -L 8765:127.0.0.1:8765 user@server` и открыть localhost; для такого теста оставьте PUBLIC_ORIGIN пустым.

Если прокси находится на другом сервере, задайте `REVIEW_DECK_BIND_IP` равным приватному IP и ограничьте firewall доступом только с IP прокси. Не публикуйте HTTP-порт приложения в интернет. Если прокси сам в Docker, его `127.0.0.1` относится к его контейнеру: подключите его к сети Compose и используйте upstream `review-deck:8765`.

## Данные и перенос существующей медиатеки

В контейнере `/library` — read-only bind mount исходников; `/data` — отдельный writable bind mount. В `/data` лежит **содержимое** прежнего `_review`, без дополнительного уровня `_review/`:

- `marks/`, `marks@review/` и любые `marks@<timeline>/` — разметка;
- `config.json`, `config@*.json`, `catalog.json`, `ids.json` — настройки и связи;
- `drawings/` — нарисованные кадры;
- `all.json` — совместимый экспорт основной ленты;
- `thumbs/`, `sprites/`, `proxy/`, `avatars/`, `meta.json` — пересоздаваемые кеши;
- `.server.lock` — блокировка одного экземпляра, не удаляйте при работающем сервере.

Остановите старый и новый серверы перед копированием. Сделайте копию исходного `_review` и скопируйте **его содержимое** в пустой каталог данных:

```sh
sudo cp -a /srv/media/_review/. /srv/review-deck-data/
sudo chown -R 10001:10001 /srv/review-deck-data
```

Относительные пути к видео должны остаться прежними. Имена папок, JSON-форматы, идентификаторы и горячие клавиши сохраняются. Абсолютные `path`/`png` в старых JSON могут указывать на прежний хост; приложение использует относительные пути, а `path` обновляется при сохранении. Агентам и другим внешним потребителям нужно сопоставлять `file` с новой медиатекой. Существующий `all.json` экспортирует только основную ленту; правки хранятся отдельно в `marks@review/`, поэтому для полного переноса/backup копируйте весь каталог данных.

Каталог данных закреплён за одной медиатекой. Для другой медиатеки нужен другой каталог данных и отдельный экземпляр с другим именем Compose/портом. Символические ссылки, ведущие за пределы медиатеки или подкаталога данных, запрещены; реальные NAS-каталоги подключайте как часть самой медиатеки.

## Резервная копия и восстановление

Для согласованной копии остановите приложение. Видео и конфигурацию развёртывания храните в резервной копии отдельно от данных. Сам экспорт `all.json` не заменяет backup.

```sh
docker compose stop review-deck
sudo tar -C /srv/review-deck-data -czf review-deck-data-backup.tar.gz .
docker compose start review-deck
```

Скопируйте `.env` и `secrets/review-password.txt` в защищённое хранилище. Они не должны попадать в Git, Docker build context и публичные вложения.

Восстановление: остановите приложение, распакуйте архив в **новый пустой** каталог, верните владельца UID/GID из `.env`, укажите восстановленный каталог в `.env`, затем `docker compose up -d`. Проверьте вход, количество файлов, обе ленты разметки, каталог, рисунки и воспроизведение видео. Исходники должны быть доступны с теми же относительными путями.

## Обновления и закрытая сеть

Перед обновлением сохраните backup и текущий образ (`docker image save review-deck:local -o review-deck-previous.tar`). Затем перенесите новые исходники и выполните `docker compose up -d --build`. Для отката загрузите сохранённый образ и запустите `docker compose up -d --no-build`; при несовместимой версии данных восстановите соответствующий backup. Автоматического обновления нет.

Для изолированного сервера соберите образ на машине с интернетом, сохраните `docker image save review-deck:local -o review-deck-image.tar`, перенесите архив и проект, загрузите `docker image load -i review-deck-image.tar` и запустите `docker compose up -d --no-build --pull never`. В этой сети используйте свой TLS-прокси/внутренний CA. Контейнеру во время работы внешние сервисы не нужны.

Версия Waitress закреплена в `requirements.txt`; базовый образ Python и пакеты ОС получают исправления при новой сборке. Для воспроизводимого повторного развёртывания одной версии сохраняйте готовый образ. Контейнер работает без root, с read-only файловой системой и ограничениями памяти/CPU/процессов; лимиты в `compose.yaml` можно адаптировать под размер видео и число посетителей.

Смена пароля: замените secret-файл и выполните `docker compose up -d --force-recreate review-deck`. Старые сохранённые браузером credentials перестанут подходить. Логин/пароль общий: отдельных пользователей, ролей, SSO и журнала действий пока нет. Для персонального контроля доступа используйте корпоративный шлюз или отдельное расширение приложения.

## Ограничения и проверки

Это один экземпляр для небольшой доверенной команды, с файловым JSON-хранилищем. Записи и экспорт сериализуются и публикуются атомарной заменой файла. Разные видео можно размечать параллельно; одновременная правка одного видео несколькими вкладками использует последнее сохранение, без слияния конфликтов. Не запускайте несколько контейнеров на одном каталоге данных. Общие сетевые ФС должны поддерживать POSIX-блокировки и атомарный rename; предпочтителен локальный диск для `/data`, NAS — для `/library`.

Превью создаются до 3 задач одновременно, тяжёлый прокси — один. Короткие видео/небольшая команда — целевой режим; тяжёлая массовая транскодировка, большие команды, RBAC/SSO и HA требуют отдельной доработки. Очередь прокси живёт в памяти: при перезапуске незавершённый прокси нужно запросить повторно.

Проверка на синтетическом видео, без пользовательских материалов:

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v
```

Нужны ffmpeg/ffprobe в PATH и возможность слушать localhost. Тесты запускают настоящий Waitress, проверяют пароль, блокировку медиатеки, выход за границы через пути/симлинки, HTTP Range/HEAD, конфигурацию, обе ленты, каталог, метаданные/превью/прокси, параллельные записи, перезапуск, защиту от чужого origin и ограничения входных данных. Проверка контейнера отдельно: `docker compose config --quiet`, сборка, `docker compose up -d`, `docker compose ps`, авторизованный просмотр через ваш HTTPS-прокси.

Локальный режим по-прежнему запускается `python3 server.py /path/to/library`: localhost, без пароля и без внешних Python-зависимостей; данные лежат в прежнем `_review/`. Для доступа по сети используйте `--on-prem`, который требует медиатеку, отдельный каталог данных и файл пароля.

Для повторения этих же сценариев внутри контейнера: `python tests/container_check.py --build` (нужны Docker и ffmpeg на хосте). Скрипт создаёт временную медиатеку и временный Compose-проект, затем удаляет тестовые контейнеры.

Дополнительная браузерная проверка: `tests/onprem-ui.mjs` для Chrome и puppeteer-core. Запускайте только на тестовой медиатеке — она сохраняет тестовую метку. Пароль задаётся переменной `REVIEW_DECK_TEST_PASSWORD`, адрес и путь скриншота — позиционными аргументами.
